## 0. 审查结论与本次纠偏

**原规划不足以交付预期的审美升级，需要把实际视觉重设计放到实施主线。** 原作者发现的缺陷、控件混用和颜色问题有价值，应保留处理；规划还需要明确新版界面如何组织、哪些地方会产生可见改变，以及怎样判断新设计更好。

| 原规划的缺口 | 对执行的影响 | 本版调整 |
| --- | --- | --- |
| 前半段集中于缺陷，之后以令牌归档和控件替换为主 | 完成许多技术工作，界面仍然接近原貌 | V1 先交付具体视觉方案与原生样板，技术缺陷另列 |
| “质感”“克制”“果冻”没有逐界面落地要求 | 实现者可以仅调整色值、圆角和动画时长 | 给出页面重设计重点、静态与动态交付物 |
| 尚未设计就确定五档圆角、三档按压和全量映射 | 统一了旧界面的规则，难以产生新的视觉层次 | 从样板提炼令牌，保留合理例外 |
| 对现有实现的保护比视觉改动空间更具体 | 容易把“保住功能”理解为“保留当前布局” | 功能、数据和交互契约稳定；布局与视觉语言可以重新设计 |
| 将截图数量、替换数量和测试通过当成主要证据 | 无法回答实际是否更精致、更好读、更跟手 | 同内容前后对比、真实操作录屏、可安装的核心链路 |
| 星岛与次级页面只有检查提纲 | 可能在换完公共控件后就宣布全 App 完成 | 各页单独交付主场景，未覆盖项明确列出 |

原来的“步骤 1–10”移到技术清单中，简称 T1–T10。下文 **V1–V6** 是新的实施顺序。技术修复继续有独立提交与证据；视觉升级的完成度由实际界面和操作体验判断。

## 1. 要形成的整体观感

这次应形成一套能辨认出变化的 Aster 新前端：暖纸底色、清楚的中文排版、适量的陶土强调、轻盈的浮层和细腻的触摸反馈。Claude 提供阅读与空间气质的参考，苹果式果冻触感体现在柔软、连续、可中断的操作反馈中；Aster 自己的星标、星岛和 Clawd 继续承担识别度。

### 1.1 静态设计需要发生的改变

- **版式：** 重新处理页头、正文、输入区和辅助区的关系，让视线能自然找到内容与下一步操作。
- **排版：** 建立标题、阅读正文、控件文字、说明和技术信息的清楚层级；中文、英文模型名与数字相互协调。
- **留白：** 主动决定疏密节奏，兼顾小屏与长文，避免所有区域都按同一种间距堆叠。
- **材质：** 纸面、嵌入区域、悬浮控件有适当区别；边框、阴影、高光和半透明共同服务于层次。
- **形态：** 按用途设计按钮、胶囊、卡片和弹层的比例与轮廓，再形成公共规则。
- **深色：** 为暗色表面建立独立的层次、前景与强调关系，使其也具备温润和清晰的观感。

### 1.2 动态设计需要发生的改变

触摸后有及时反馈，展开能看出来源，收起能理解去向，快速操作可以反向或取消。小控件、输入胶囊、浮层和整页应有不同的重量感；文字与编辑内容保持稳定清晰。

布局、轮廓、阴影和动画均允许调整。既有模型效果、请求策略、数据、草稿与输入法状态继续保持可靠。具体技术边界见技术清单，不要求在每次调整视觉前重新审查全部业务。

本轮查看了本地 `artifacts/design-upgrade-20261110/` 中三张界面总览，以及输入胶囊和输入选项的单页截图，并抽查相关源码。以下是**针对历史截图的设计判断**，不是新一轮设备实测，也不代表所有状态都存在同样问题。

| 画面 / 状态 | 现有观感与问题线索 | 规划中的设计动作 |
| --- | --- | --- |
| 聊天首页与输入展开 | 星标、问候和输入区已有品牌基础；展开壳体的描边与阴影较重，工具的形态与权重仍可整理 | 重新安排空态重心与输入区比例，精修壳体层次、工具组织及主操作 |
| 输入选项 / 剧情工具 | 多个工具使用接近的面积与强调程度；大格子、说明和独立开关区形成较长操作面板 | 根据高频、调整项和低频管理重新分组，减少同权重卡片堆叠 |
| 模型选择 | 服务卡、模型卡、选中标记、上下文与管理入口都占据注意力 | 优化选择顺序与信息密度，让当前模型、服务归属和下一步更清楚 |
| 侧栏 | 功能齐全；工作区、筛选、搜索、会话及底部入口的层级还有设计空间 | 重设计导航与内容列表的关系、选中态、行间节奏和品牌头部 |
| 阅读与表格 | 阅读已有统一基底；表格容器头和附属操作带来额外视觉重量 | 系统调整正文、内容块、思考区和消息操作的节奏，不把表格头当成唯一美化项目 |
| 创作 / 下载 / 设置 | 暖色与卡片已有共性，主场景的内容与操作关系仍需逐页设计 | 分别围绕创作画布、任务进程和配置查找重排，避免只做控件替换 |
| 深色 | 已有主题，但表面层次、次级文字和选中强调还需按实际场景精修 | 单独核对代表画面，HTML 和星岛另外确认 |

### 2.1 不把截图条件误当成设计缺陷

- 首页顶部“新对话默认使用……”经源码核对是模型选择后的临时 Snackbar，不是常驻导航栏。重新拍摄常态首页时应等待该提示消失；提示本身可另作状态样例。
- 输入截图为空草稿，发送按钮是禁用态。需要另拍有效草稿状态，才能判断主操作的实际对比和权重。
- 当前两张 RP 截图停留在 HTML 加载占位，无法据此评价加载后卡片的质感与深色可读性。
- 现有侧栏样例为空历史或单条记录，还需要少量多条历史样例来判断列表层级、长标题与分组。
- 模拟器截图可以支持静态审阅；手感、真实震感和性能结论需要对应的运行证据。

这组历史素材保留作参考。核心对比仅补足上述缺失状态，不为重新规划再跑一整轮页面测试。交接给其他环境时，附带去敏后的基线素材，不能假定 Git 仓库包含本地 artifacts。

## 3. 第一轮必须具体设计的界面

第一轮以**聊天阅读、输入展开、工具面板、非空侧栏**四个画面作为优先视觉交付；随后连成包含首页、模型选择和 RP 的核心原生链路。每个画面需要说明版式、层级与材质为何这样调整。

### 3.1 聊天首页与阅读

**首页设计动作**

- 调整星标、开场文字、可选快捷开始与输入区的纵向关系，使空白承担明确的空间节奏。
- 顶栏明确会话身份、模型与主要操作的权重，长模型名和大字号仍有清楚布局。
- 快捷开始只在有价值时加入，进入可编辑草稿；保留干净空态和星标交互的设计空间。

**阅读设计动作**

- 重新设计标题、正文、引用、代码、表格、思考和消息操作之间的节奏。
- 用排版和留白建立层级，决定哪些块需要表面、细边界或背景，哪些可以直接融入阅读流。
- 调整用户消息的宽度、内边距和表面处理，与助手正文形成清楚关系。
- 将高频消息操作组织得轻量、可发现；操作出现或折叠时保持阅读位置稳定。
- 选取同一段含中文长文、列表、引用、代码和表格的内容做前后对比，保留用户阅读偏好。

**可见交付：** 首页构图与阅读层级有清楚的设计决策；同一段内容在新版中的主次、疏密和容器处理可直接比较。

### 3.2 输入胶囊与 Clawd

- 重设计收起、聚焦、输入多行、带附件、生成中五种状态的比例与层次。
- 调整壳体的边缘、高光与阴影，使悬浮感轻盈，并与页面纸面相区分。
- 重新组织附件、思考档位、扩展编辑、发送/停止的权重，输入区域保持主导。
- 壳体可以柔软形变，文字、光标、选区和中文组合输入保持稳定；Clawd 的位置、尺寸与活动强度跟随实际输入空间协调。
- 以一次连续录屏展示点击聚焦、输入、开关工具、收起键盘、继续输入和发送/停止。模型请求不等待装饰动画结束。

**可见交付：** 五种状态形成同一个控件的自然变化，壳体材质、操作组织和焦点过渡都有可辨认的改进。

### 3.3 工具面板与模型选择

**工具面板**

- 重新区分附件操作、即时调整、会话开关与低频配置，决定各组使用紧凑行、工具按钮或完整设置项。
- 调整图标、文字、说明、分组标题和关闭入口的比例，降低所有项同时被强调的情况。
- 同组对齐、组间留白与滚动区域保持连贯；重要操作清楚，低频配置仍然容易到达。
- 对话和 RP 使用同一设计语言，容纳各自不同的内容，不强制复制相同格子数量。

**模型选择**

- 以当前模型为主要信息，清楚表达所属服务、可用模型和配置入口。
- 多服务、多模型时仍易搜索与定位，压缩无助于当前选择的重复摘要。
- 选中态、可点击区域、加载和错误有明确反馈，服务分配和模型路由沿用现有约定。

**可见交付：** 分类与选择顺序得到重新设计；在有限视口中能找到高频操作，辅助信息的权重清楚。

### 3.4 侧栏与导航

- 重排品牌头部、工作区入口、搜索、筛选、会话和底部设置之间的关系。
- 为选中工作区和当前会话分别建立适合其层级的状态，控制强调色与底色的使用范围。
- 用非空样例检查长标题、分组、置顶、收藏、归档和菜单，操作层级与列表节奏一起设计。
- 搜索键盘出现、结果为空和侧栏拖动时，主要内容保持可达；导航反馈与页面转场协调。

**可见交付：** 用户能更自然地分辨“去哪个工作区”“找哪段会话”和“管理设置”，页面内的对齐与疏密经过重排。

### 3.5 RP 阅读与角色配置

- 将阅读、角色身份、回复切换与剧情操作形成协调布局；角色配置面板使用相同视觉系统。
- 检查长文与 HTML 状态块混合时的前后间距、加载过渡和操作区域，避免 App 容器盖过内容。
- 角色卡自己的 CSS 与脚本行为保持兼容，App 外壳的设计调整不强行覆盖卡片内部风格。
- HTML 高度和默认颜色按技术清单处理。没有加载后的证据时，RP 卡片验收仍为待完成。

**可见交付：** RP 的 App 外层阅读体验与新版聊天协调，角色内容保留自己的表达空间。

## 4. 重新组织实施顺序

| 阶段 | 实际工作 | 阶段交付 |
| --- | --- | --- |
| **V1 视觉重设计与首个原生样板** | 优先完成四个代表画面的重设计；直接落地至少一条可运行的阅读/输入/工具链路 | 同内容前后对比、设计取舍说明、首个可安装样板 |
| **V2 核心链路与动效** | 补齐首页、模型选择、侧栏和 RP，完成输入、弹层、转场与重内容衔接 | 核心链路预览包、短录屏、浅深色代表画面 |
| **V3 提炼设计系统并扩散** | 从实际样板确定令牌、组件与状态；迁移可复用实现 | 代码对应的设计规则、公共组件及受影响页面 |
| **V4 全 App 逐页升级** | 创作、下载、设置、星岛与次级面板分别完成主要场景设计 | 各页可见变化、主要操作演示、覆盖与待办清单 |
| **V5 必要回归与真机精修** | 按改动风险检查数据、输入与交互，定位实际卡顿并精修 | 针对性验证记录、真机体验与剩余问题 |
| **V6 交付与正式发布准备** | 整理源码、构建、对比与说明；按后续明确要求合并发版 | 可复现的最终包、更新记录和未完成项 |

### 4.1 避免实施顺序再次偏离

- 第一轮先展示具体视觉变化，不能等圆角归档、所有输入框迁移和全量测试整理全部完成后，才交出新版界面。
- 先以一套主推设计直接做原生样板，必要时给局部备选；避免在首个可见成果前先写一整套长篇设计报告或重新走查所有页面。
- 只有崩溃、数据风险或阻断当前样板操作的缺陷需要插队处理。其余技术项可以独立推进，但应与视觉交付分别记录。
- V1 与 V2 可以有必要的小范围共用组件调整；V3 承接经过实际界面检验的规则，不要求重复实现样板。
- 普通视觉选择由实施者自主判断，提供可体验结果和取舍依据；样板交付后可继续推进方向明确的工作，不必为每个参数停下来等待确认。
- 功能删减、请求策略或数据迁移属于另一个决策范围，发现需求时单独说明。
- 提交按可理解、可回退的改动分组，预览包按阶段生成，不要求一个步骤只允许一个巨大提交。

时间有限时，优先把 V1–V2 做成完整、稳定且明显提升的成果，再扩展覆盖面。没有重设计的页面继续列为未完成，公共组件变化不能自动替代该页的验收。

## 5. 全 App 扩展的逐页设计任务

| 页面 | 必须具体处理的设计 | 应展示的状态 |
| --- | --- | --- |
| 创作 | 模型/模式、描述、参考图、参数和主操作重排；预览和任务区拥有适合图片创作的空间 | 输入与参数展开、生成中、完成预览、失败恢复 |
| 下载 | 输入、解析、选择与任务列表形成清楚流程；平台标记和辅助信息保持次级权重 | 待输入、解析结果、任务进行、历史与媒体预览 |
| 设置 | 重排组别、列表行、摘要和表单；区分服务连接、模型分配与偏好 | 首页、搜索结果、服务编辑、密码/错误/键盘 |
| 星岛 | 精修入口、纸面层次、轮廓形变、内容出现和收起；保持与主 App 的视觉联系 | 常驻、展开、快捷问答、框选、收起及反向 |
| 次级面板 | 预设、技能、插图服务、文件与确认面板复用新语言，保留各自内容结构 | 代表性选择、编辑、长内容与错误状态 |

星岛需检查实际窗口与 View 实现；只同步一组色值不能标记这一行完成。Clawd 与输入胶囊的协调已纳入核心链路，星岛阶段再检查其相关独立场景。

## 6. 动效设计与加载策略

为每类对象记录“起点/终点、驱动方式、中断行为、内容如何跟随、关闭动画时如何呈现”。参数先在样板中调整，再进入共用规则。

| 对象 | 需要设计的体验 | 可观察的验收 |
| --- | --- | --- |
| 按钮与分段控件 | 轻压、释放与选中移动有合适重量，触觉绑定有效操作 | 滚动取消无误点击，连续操作不残留形变 |
| 输入胶囊 | 外壳、焦点、工具与键盘协调变化 | 中文输入、光标和选区稳定，开关输入法不突跳 |
| 弹层与侧栏 | 来源清楚、跟随拖动、释放后自然收敛 | 可中途关闭或反向，视觉与点击区域一致 |
| 页面切换 | 少量位移、明确层级、内容及时可用 | 快速切换到达最后目标，旧页不长期遮挡 |
| 图片与 HTML | 尺寸占位、首帧和加载完成有连贯交接 | 保留阅读位置，不把占位截图当成内容完成 |
| 星岛 | 轮廓、窗口内容和入口存在连续联系 | 开合与反向连续，框选和确认区域准确 |

可以参考任务书的建议时长；大面积长文表面应稳定，小控件允许更活泼。保留系统关闭动画后的完整功能反馈。

先定位主线程、重组、测量和重内容初始化开销，再选择动画与加载方式。对必要等待使用稳定占位、保留内容和柔和渐显；业务状态、错误和操作反馈及时显示。软件渲染模拟器用于检查轨迹和布局，不提供真机帧率结论。

## 7. 视觉验收如何落地

### 7.1 对比材料

核心对比使用相同文案、草稿、消息、模型与窗口尺寸。等待临时 Snackbar 消失，并同时准备空态和有内容状态。保留截图对应的提交、主题、字号与夹具说明。

V1 优先交聊天阅读、输入展开、工具面板和非空侧栏的前后对比；V2 补充模型选择、RP 和一个深色代表画面。覆盖到的其他页面随阶段补充，不反复重拍未受影响区域。

另提供少量连续录屏，展示输入/键盘与弹层、页面/侧栏，以及 RP 重内容或星岛的代表过程。仍为占位、缺失状态或录制失败的项目标为未覆盖。

### 7.2 每个代表画面的四个问题

1. **看哪里：** 第一、第二、第三层信息是否更清楚，主操作是否容易识别？
2. **怎样读：** 中文排版、密度、对齐和内容块之间的节奏是否更舒适？
3. **什么层次：** 纸面、嵌入内容和悬浮控件是否协调，边缘与强调是否合适？
4. **怎样动：** 按压、展开、键盘和转场是否连续，用户能否随时继续操作？

比较时由实施者明确写出“改了哪里、为什么这样改、对比证据是什么”，并保留产品负责人的主观判断。审美没有由替换数量自动计算的合格分；使用者对方向有明确反馈时，要据此调整样板。

如果某个画面只发生颜色或圆角替换，应按实际范围称为局部修整；只有该画面的构图、层级、排版或材质经过设计并取得可见改善，才标记为完成质感升级。可以有依据地保留原有好设计，无须为了制造差异更改每个元素。

## 8. 技术支线、验证成本与产品边界

技术清单保留 HTML 高度与权限、默认颜色、触觉、组件语义、对比度及既有测试失败的详细证据。它们与视觉样板共同保证可用性，不替代视觉交付。

- 当前基线为分支 `design/upgrade-20261110` 的 `cb60f96`；main 为 4.3.4 / 89。历史材料记录 856 项 JVM 检查通过，以及 37 项设备测试中 12 项既有失败；本轮没有重跑。
- 日常只运行与改动有关的检查。文档审查不构建 App；样式分组修改后编译并检查代表画面；脚本权限、原生桥、输入和生命周期改动有相应定向回归。
- 既有失败继续按过期断言、环境条件和实际缺陷分类，关联的真实问题仍要处理，不为升级而批量删除测试。
- 模型效果、服务分配、请求与计费策略、数据、包名和发布签名保持既有约定。旧故事模式不恢复；现用剧情 RP 纳入升级。
- 角色卡脚本授权、原生能力和沙盒限制按技术清单验证。不能用视觉改动扩大权限。
- 正式推送、合并与发版另定。届时核对最新版本递增规则，更新日志和版本标识；当前规划不指定 4.5 或锁定 versionCode 90。
