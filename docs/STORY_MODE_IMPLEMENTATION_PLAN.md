# Aster 故事模式：设计与实施交接计划

文档版本：1.0。状态：需求与架构方案，待执行模型核对仓库。

## 0. 交接边界与项目约束

本文件供其他模型实施。规划端本次不修改应用代码，不声称已检查最新仓库、编译或发布。仓库：https://github.com/adongshaln/Aster 。Android 包名保持 com.adong.adchat。

执行前读取 AGENTS.md 和最新 main，记录基线 SHA、实际版本号、构建方式。历史对话提到 2.3.0，但不以聊天摘要代替仓库事实。保留已有脏工作区，必要时建立干净 worktree；禁止 reset --hard 清除用户内容。沿用仓库当前固定签名配置，不生成新密钥，不输出凭据。每阶段及时保存、提交，测试 APK 与正式发布分开；正式推送、合并和发布遵循用户当前授权。

用户目标：用户提供剧情方向、对白、人物行动或世界观补充，模型续写故事；用户也需要先讨论设定，或中途暂停正文商量下一步。主要使用兼容网关上的 Gemini Chat Completions。不要把它误做成提示词编辑器。

## 1. 产品原则与首版范围

- 自动维护资料，但不擅自决定哪些讨论方案正式成立。
- 讨论不等于剧情；未来计划不等于已经发生；世界事实不等于所有人物都知道。
- 正文流式输出，后台整理独立执行，不向正文夹带记忆 JSON 或管理过程。
- 所有记忆可追溯、可修正；有效记忆必须对应当前有效的正文版本。
- 保持现有暖色、克制的聊天视觉风格。不要新增遮挡正文的悬浮控件、重阴影胶囊或大量常驻按钮。
- 复用现有 Chat 请求、消息、重试和版本能力；不能为新功能重写整个网络层。

首版交付：故事入口、讨论/正文工作区、故事档案、候选确认、上下文选择、后台增量记忆、变更查看、重写一致性及失败恢复。分支按钮、关系图、向量检索、附件解析、多人协作和自主多 Agent 循环均延期。数据结构为将来的分支保留边界。

## 2. 用户流程与界面

### 2.1 创建与切换

新建入口提供普通聊天与故事创作。故事只需名称即可建立，允许稍后命名；使用当前可用模型配置，不绑定某个具体 Gemini 名称。默认打开“讨论”，不要求先填完整人物表。顶部提供“讨论 / 正文”切换和故事档案入口；沿用原输入胶囊、键盘与边缘显示机制。

两个工作区各有消息记录和草稿，切换时保留滚动位置、未发送内容。切换不取消已经开始的请求，也不能让回复落入错误工作区。新故事的正文空态提供“开始正文”；若存在草案，只提示可查看，不强制确认所有资料。不得因为切换标签自动发送生成请求。

### 2.2 讨论工作区

用于比较设定、询问合理性、讨论文风和计划。模型可以提供示例片段，但示例不是正式正文。后台提取候选项、明确决定和讨论摘要。候选卡片在相关回复下折叠显示，例如“3 项待定设定”，提供逐项采用、编辑后采用、废弃；不要每轮弹窗。

用户自然语言明确决定且指向唯一候选时可自动采用，显示可撤销记录；“这个不错”指向不明时只追问对应内容，不批量采用模型整段建议。候选模型返回的“已确认”标签本身不能作为授权证明，必须关联用户明确决定的来源。用户纠正优先。

### 2.3 正文工作区

用户正常引导剧情，模型创作。正文回复菜单复用复制、重写能力，并增加“讨论这段”和“本轮记忆”。后台状态放在档案入口附近，不遮挡输入框，不抢焦点；详细错误放入档案变更页。

“讨论这段”记录选中内容、消息版本与剧情位置，跳到讨论；讨论不会自动改正文。讨论确定后提供“用于后续”“重写原段”“修改设定”三个明确动作。首版的重写原段可以重生成所在整条回复，不承诺精确局部替换；保留原版本。

### 2.4 故事档案

四区：设定（世界、规则、计划）、人物（档案、关系、认知）、剧情（场景、事件、未完事项）、变更（自动更新、候选、冲突、失败）。列表先行，不做关系图。条目支持来源查看、修正、固定与撤销；用户能区分自动记录和自己确定的内容。涉及后续依赖的撤销不能直接删一个数据库行，应展示影响并重建状态。

## 3. 记忆模型

建议逻辑实体如下；实际类名和持久化框架由 M0 决定，不要求照搬。

| 实体 | 用途与必要边界 |
| --- | --- |
| Story | 故事身份、模型配置引用、创建信息 |
| Timeline | 当前路线与父路线/分叉点预留；首版只有默认路线 |
| MessageRevision | 消息身份、版本、工作区、所属路线、有效性、生成状态 |
| Entity | 人物/地点/组织的稳定 ID、名称、别名；同名不自动合并 |
| MemoryRecord | 类型、内容、实体引用、作用范围、来源、信息性质、生效位置、是否固定 |
| Proposal | 候选设定、候选计划、决定来源、待定/采用/废弃/被替代状态 |
| MemoryChangeSet | 一次原子变更、基础版本、来源版本、操作列表、状态 |
| Snapshot | 某有效位置的资料快照与日志游标，加速恢复 |
| MemoryJob | 输入来源、任务状态、重试次数、去重键、待处理范围 |

MemoryRecord 类型：世界事实、人物档案、当前状态、有向关系、人物认知、剧情事件、未完事项、作者计划、摘要。

每条记录区分：用户明确设定、正文已发生、人物主观相信、未知/推测。关系为 A→B，带依据，不强制好感度分数。伤势、位置、物品属于随剧情变化的状态，不覆盖为永久人物特征。事件顺序使用应用生成的序号；没有明确日期不得捏造日期。

“固定”表示优先进入上下文且禁止自动覆盖，不表示能无限塞入请求。固定内容本身超预算时明确告知并引导缩减，不能静默丢弃。

所有来源引用真实消息版本与文字片段；应用验证来源存在、作用范围正确。正文开始前的设定与开始后的设定修订都要保留生效位置，不能把后来决定无条件回填到过去。

## 4. 讨论、计划与正文的隔离

讨论候选只参与相关讨论检索；正文仅使用已确认设定、适用计划和有效剧情。废案保留审计记录，但不作为正文事实检索。

例：“让她成为公主好吗？”→候选；“采用失去继承权的旁系设定”→确认；“以后让她背叛，现在不要揭露”→作者计划，记录时机约束；实际背叛写入有效正文后→事件。作者计划不进入人物认知，不允许提前兑现。

用户明确纠正 > 用户确认设定 > 有效正文事实 > 后台推测。此顺序用于冲突处理。正文与确认设定矛盾时保留冲突及来源，不默默覆盖；后台推测不能创建隐藏身份、死亡、恋爱关系等重大事实。

讨论上下文包含相关正式资料、有关候选、讨论摘要与近期讨论；需要分析正文时只取指定剧情及必要上下文。正文上下文不包含整段讨论历史，以免模型采用废案。讨论也不能读取当前路线之外的未来事件并当作已发生。

## 5. 请求与后台流水线

### 5.1 创作请求

顺序建议：创作规则→固定设定→当前场景→相关人物/认知/关系→相关世界资料与适用计划→早期摘要→近期完整有效正文→本轮用户输入。资料块标明用途，使用实体 ID 关联。不要硬编码强势文风、替用户控制角色、擅自推进计划。

讨论使用独立的组织规则。两类请求都使用已有 Chat 通道；请求路径、参数和流式结束标志通过真实配置验证。不要假定网关支持特定 schema、tool calling 或特定模型上下文窗口。

### 5.2 整理请求

输入：工作区、本轮有效输入与完整输出、相关旧资料、基础记忆版本、输出结构。输出：新增/更新/结束条目、候选项、明确决定和冲突。禁止模型直接写数据库、执行任意工具或读取外部文件。

应用验证：格式与大小限制、允许的操作类型、实体引用、真实来源、范围、固定资料保护、基础版本、幂等键。创建实体和引用它的记录需在同一变更内可解析。全部通过后事务保存；部分非法不允许写出半次更新。失败任务可重试，正文仍保留。

格式约定包含 schemaVersion、operations、conflicts；storyId、timelineId、sourceRevisionId、baseVersion、jobId 由应用绑定，不能信任模型返回值。更新操作指定目标 ID，禁止按模型给出的名称随意更新同名人物。

### 5.3 完成与竞态

正文完整结束才触发正式记忆整理。取消、截断或网络失败的草稿不作为完整事件；提供继续/重试能力时，最终有效版本完成后再处理。后台任务按路线串行更新；请求输入快照固定。下一轮在整理未完时使用最后有效记忆加尚未整理的完整消息，不阻塞用户。

任务完成时再次检查来源版本是否仍有效；重写期间旧任务到达必须丢弃或转为历史记录，不能生效。版本过期则重新组织输入，不能盲目覆盖。重试有上限，持久化待处理状态，重启可恢复。利用已有 Android 后台机制，遵守系统调度限制，不承诺应用被强停后仍实时执行。

## 6. 检索与成本

首版采用名称/别名匹配、当前场景、在场实体、关联关系和未完事项选择资料。保存前全局去重检查只限本故事适用范围，不因当前检索没命中就重复创建人物。实体合并不确定时保留候选映射，避免错误合并。

为输出预留预算，输入按优先级裁剪：先减少低相关旧事件，再压缩旧对话；近期未整理内容不得在无替代摘要时静默丢弃。摘要记录覆盖的消息版本范围，源版本改变即失效。单独摘要任务按长度阈值触发，不每轮重写整个故事。

默认每轮至多一次正常整理调用；重试和摘要另行计数。默认同一服务商配置，允许用户以后单独选择整理模型，不自动把故事发送到另一服务商。设置提供自动记忆开关、状态与重试。关闭时仍保存消息和待处理范围，再开启可补齐。API 有用量时显示实际值，否则标记估算或未知。

## 7. 重写与版本恢复

保留原回复，新回复产生新版本。有效记忆由当前路线的有效消息版本、确认决定和记忆日志共同决定。切换版本恢复最近适用快照并重放有效日志；不能只切换屏幕文字。

编辑较早输入或重写中间回复会影响后续链。首版安全行为：保留旧后续为历史，新的有效路线从该点继续；明确告知影响，不能自动把旧后续接上新版本。若仓库已具备分支模型，优先复用。

正文派生记忆随版本失效而失效。独立于该正文的用户世界设定应保留；引用旧剧情作出的讨论决定需标记待复核，不能全删或无条件继承。摘要同样必须失效重建。设置修正影响历史时提示受影响位置；修正档案不等于重写正文。

## 8. M0：仓库核对任务

读取最新 main 和仓库规则，确认以下内容并记录真实路径：

1. 消息存储及数据库迁移、现有备份/恢复/删除流程。
2. 对话/模型配置、Chat 与 Responses 路由。
3. 流式完成、停止、失败、重试的判定。
4. 消息编辑、回复版本、分支及滚动状态。
5. 后台调度、网络请求生命周期、依赖注入能力。
6. 主题组件、设置与页面导航、输入草稿。
7. CI、固定签名、当前版本与测试 APK 流程。

M0 产出实际文件映射、复用/新增清单、数据迁移方案、风险及预计提交拆分。不得仅凭本计划臆造文件名。保护老对话，默认迁移为普通聊天；旧备份导入的缺省字段必须兼容。新故事数据若暂不支持导出需明确说明，不能让现有备份界面误称已完整备份。

## 10. 验收用例

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| A01 | 讨论“也许她是公主”，切到正文 | 候选保存，正文不把她当公主 |
| A02 | 明确采用一个候选 | 仅该项确认，关联用户决定，可撤销 |
| A03 | 多方案后说“这个不错” | 不整批采用；指向不明时澄清 |
| A04 | 讨论输出示例场景 | 不进入已发生事件 |
| A05 | 计划背叛但暂不揭露 | 仅作者计划，不提前发生、不扩散认知 |
| A06 | A怀疑B偷钥匙 | 保存怀疑，不确认B偷窃 |
| A07 | 同人不同别名/不同人同名 | 不重复或错误合并，关系方向正确 |
| A08 | 正文与固定规则冲突 | 保留规则并标记冲突，不自动覆盖 |
| A09 | 重写导致受伤情节消失 | 伤势及派生摘要撤回 |
| A10 | 整理中切换版本 | 旧任务不能污染新版本 |
| A11 | 整理期间发下一轮 | 使用未整理正文，不丢上下文或乱序覆盖 |
| A12 | 返回非法 JSON/无效 ID | 无半次数据库更新，失败可重试 |
| A13 | 重试同一任务 | 不重复添加人物或事件 |
| A14 | 取消输出、重启应用 | 未完回复不记为完整事件；任务恢复可靠 |
| A15 | 编辑旧输入 | 旧后续保留但不混入新路线 |
| A16 | 切换讨论/正文与键盘 | 草稿、回复目标和滚动位置正确，无遮挡 |
| A17 | 正文包含指挥记忆器的对白 | 仅作为故事内容，不执行越权修改 |
| A18 | 超长上下文与固定内容超预算 | 不静默丢关键设定，给出明确处理方式 |
| A19 | 老普通对话、备份导入与删除 | 行为兼容；删除故事同时处理相关任务与档案 |
| A20 | 修改独立世界设定后重写正文 | 不误删独立设定；旧剧情关联决定标记复核 |

自动测试重点：数据迁移、原子性/幂等、失效恢复、上下文隔离与预算。人工测试重点：真实网关流式、长文滚动、键盘、主题及读写流程。不要通过仅包含硬编码正确答案的 mock 来声称模型整理准确；使用虚构样本做一次真实端到端测试并记录局限。
