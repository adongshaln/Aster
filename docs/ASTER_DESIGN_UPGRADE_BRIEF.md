## 3. 设计方向：把“质感”落实到具体选择

### 3.1 Claude 方向：阅读、留白与温润秩序

参考 [Claude 官方产品界面](https://claude.com/) 的整体气质，结合 Aster 已有的暖纸、墨色、陶土色与衬线资源，建立适合中文长文本的阅读环境。

- 大面积背景温暖、平静，层级通过色阶、留白和排版形成。
- 文字拥有明确的主次关系，长中文、数字、英文模型名、代码和链接之间协调。
- 陶土色集中用于关键操作、选择和少量识别点，帮助用户判断下一步。
- 常用内容有充足空间，辅助信息安静地退到次级层级。
- 保留 Aster 的星形标志、星岛和 Clawd 等辨识度，统一它们与页面的关系。

### 3.2 苹果果冻方向：按下有反馈，变化有来处

“苹果果冻”在这里是项目期望的触感描述，具体体现为：触摸立即响应，控件有轻微压缩与回弹，浮层能跟随手势，展开和收起保持空间联系，中途反向仍然连续。

不同对象应有不同的重量感：小按钮可以活泼一些，输入胶囊可以柔软一些，整页和长文则应稳定。文字、图标和编辑光标保持清晰，外壳形变控制在舒适范围。

动效需要短促、准确、可取消，并为关闭动画的用户提供完整反馈。这与 [Apple 的动效指导](https://developer.apple.com/design/human-interface-guidelines/motion) 中强调的适度、反馈和可中断原则一致；本文具体参数是 Aster 的建议起点，需通过真机调整。

### 3.3 材质与层次

建议以温润纸面作为主体，配合细边界、柔和色差和少量悬浮阴影，建立三个清楚的层次：页面背景、内容表面、当前操作浮层。

局部半透明或磨砂可以用于浮动控件，但需要同时证明其阅读价值和性能可接受。静态渐变、轻阴影和不透明表面也可以达到所需层次；具体选择由实际效果决定。

交付时应能解释：为什么这个区域需要容器、为什么这个按钮被强调、为什么这个地方需要动画。装饰密度需要服务于长时间使用。

## 4. 建立可复用的视觉与交互系统

先形成一套小而完整的规则，再把它应用到所有页面。页面局部可以有业务差异，共用的元素应保持同一种语言。

### 4.1 基础令牌

当前 `Theme.kt` 中的核心色可作为起点，允许你基于实际观感统一调整。下表记录的是现有源码值，不是 Claude 或 Apple 的官方色值要求。

| 语义 | 当前浅色 | 当前深色 |
| --- | --- | --- |
| 页面背景 | `#F4F3EE` | `#141413` |
| 内容表面 | `#FAF9F5` | `#1E1E1C` |
| 正文 | `#141413` | `#F0EFEA` |
| 次级文字 | `#6B6860` | `#9A9890` |
| 细边界 | `#E4E1D8` | `#2E2D2A` |
| 陶土强调色 | `#D97757` | `#E28769` |

请同时统一以下规则，并沉淀到可复用实现中：

- **间距：** 建议以 4 / 8 / 12 / 16 / 24 / 32 dp 为基础，明确页边距、组间距和控件内边距。
- **圆角：** 为小控件、普通容器、浮层和胶囊分别定义少量固定档位，避免每页自行取值。
- **排版：** 定义页面标题、分区标题、阅读正文、控件文字和辅助说明。中文正文可从 16–18 sp、26–30 sp 行高试起，保留用户的字号、字体与字重偏好。
- **字形：** 衬线承担阅读与品牌气质，无衬线承担密集控件与技术信息；选择以中文可读性和真实渲染效果为准。
- **图标：** 统一尺寸、视觉重量和基线，沿用已经存在的品牌资产。
- **状态：** 覆盖按下、选中、禁用、加载、失败、完成和空内容，不能只设计默认状态。
- **深色：** 重新检查对比、强调色和层级，尤其是浮层、代码、图片边界与系统栏。

常用交互目标按 Android 的 **至少 48 × 48 dp** 要求检查，视觉图形可以更小，但不能与相邻点击区域冲突。依据：[Android Compose 无障碍默认行为](https://developer.android.com/develop/ui/compose/accessibility/api-defaults#minimum-touch-target-sizes)。

### 4.2 优先沉淀的公共组件

页面头部、品牌与模型行、主次按钮、图标按钮、分段控件、列表行、输入胶囊、选择面板、底部弹层、确认弹窗、状态提示和空状态，应使用共用实现。

组件需要有明确的样式和行为边界。业务页面提供数据与操作，通用组件负责外观、触摸反馈和基本无障碍语义。已有公共组件优先改进，必要时重构，避免继续复制出多套相似样式。

## 5. 动画与手感要求

以下是建议起点，不是强制让所有控件套用相同时长。请依据距离、对象大小和设备体验调整，并将最终规则集中管理。

| 场景 | 期望感觉 | 建议起点 |
| --- | --- | --- |
| 小按钮、图标按钮 | 按下立即轻压，松手回弹一次 | 约 2%–4% 压缩；回弹约 180–280 ms |
| 分段选择与开关 | 连续移动、清楚落位 | 约 180–240 ms，轻微弹性 |
| 输入胶囊 | 壳体柔软，编辑内容稳定 | 约 220–320 ms；与焦点、IME 协调 |
| 页面切换 | 短距离移动、层次清楚 | 约 220–300 ms，少量位移与渐显 |
| 底部弹层、侧栏 | 跟手、有阻尼、能反向 | 手势直接驱动；释放后约 240–360 ms 收敛 |
| 内容展开与收起 | 阅读位置有延续 | 约 160–240 ms；长内容避免大幅弹跳 |
| 图片、HTML 首帧 | 内容准备好后自然接替占位 | 约 120–200 ms 渐显 |
| 星岛形变 | 与摄像头入口存在连续空间关系 | 基于现有弹簧和轮廓实现调优 |

所有主要动画还应满足以下行为要求：

1. 点击后立即开始反馈，业务操作不等待装饰动画播完才执行。
2. 连续点击、快速切换和中途关闭时，轨迹连续，最终状态与用户最后一次操作一致。
3. 手势取消不会误触发按钮，滚动不会产生密集的按压震动。
4. 动画中的视觉位置与实际可点击区域一致，弹层关闭时不发生点击穿透。
5. 键盘、输入框和消息底部衔接自然，保留草稿、选区、光标及中文输入法组合态。
6. 阅读、流式输出和长列表滚动时，装饰动画保持克制；后台和不可见区域停止不必要的持续动画。
7. 关闭系统动画后，所有功能和状态仍然完整可用。

果冻效果重点放在可操作外壳及触摸反馈。长段正文、WebView 内容和整页阅读区域需要保持稳定的比例与清晰度。

## 6. 各页面具体升级要求

### 6.1 对话：作为整套设计的标杆

请先把一条完整的聊天链路做到满意：进入会话、选择模型、输入、发送、等待、阅读、查看附件、继续输入。这条链路将定义其他页面的质感。

- **首页与空状态：** 保留品牌气质，说明可以做什么，提供少量明确的开始方式；预设操作进入可编辑草稿。
- **顶栏：** 标题、模型与辅助操作层级清楚，长模型名和大字号仍然可用。
- **正文：** 优化中文长文、Markdown 标题、引用、代码、表格和图片之间的节奏；用户与助手消息容易区分。
- **消息操作：** 常用操作容易找到，次要操作适当收纳；流式结束时操作区出现自然，避免正文突然跳动。
- **思考与工具状态：** 展开、折叠和正文开始之间关系清楚；生成中的状态不会压住主要阅读内容。
- **自动滚动：** 用户回看历史时暂停跟随，回到底部后恢复；正文增长、图片加载和键盘变化不会无故把人拉走。
- **输入胶囊：** 重点打磨聚焦、收起、附件、长草稿、发送/停止、思考档位和 Clawd 的协同，保证输入区域始终可达。
- **剧情插图与文件：** 各阶段反馈真实，完成内容自然出现；失败可以恢复，长内容和预览不会带来明显布局突变。

### 6.2 剧情 RP：适合长时间沉浸阅读

- 与普通对话共享基础视觉、输入和操作语言，保留角色与剧情阅读的独立气质。
- 角色配置、预设、世界书、用户身份等复杂选项使用清楚的分组和渐进展开，日常对话界面保持轻量。
- 回复切换、重新生成、续写、编辑、隐藏及分支相关操作层级清楚，切换期间不丢失当前阅读位置。
- 角色卡 HTML 的原有样式、脚本和交互兼容性需要保留。可以优化 App 外层容器、加载和预览衔接；调整卡片内部 CSS 必须有明确的兼容理由。
- 长文、图片和复杂卡片混合出现时，优先保证滚动与输入流畅，给重内容提供稳定占位。

当前 RP 与普通聊天的能力接入并不完全一致。梳理差异时如发现新需求，请单独记录；不要在视觉升级中默认承诺功能已经打通。

### 6.3 导航与侧栏：清楚、轻快、位置稳定

- 明确区分工作区入口、会话历史和全局设置，减少同一层级里的竞争信息。
- 搜索、收藏、归档、重命名和删除容易理解；长标题、小屏和大字号下仍可操作。
- 切换页面保留合理的滚动、搜索和草稿状态，返回行为符合 Android 使用习惯。
- 手势打开、收起、搜索键盘和背景层次共同协调，避免多段动画依次等待。

### 6.4 创作与下载：突出内容和任务进程

- 绘图与漫画翻译的入口、当前模式和主要动作清楚；常用参数直接可达，高级参数按需展开。
- 任务从准备、生成到完成有真实反馈，作品预览有充足空间，失败与重试位置明确。
- 下载页围绕“输入 → 识别/解析 → 选择 → 下载 → 查看/保存”整理层级。
- 图片缩略图、播放器和大列表注意解码、复用及生命周期，滚动时不被重内容拖慢。
- 各阶段无法提供真实百分比时，用阶段说明或不定进度表达。

### 6.5 设置：能迅速找到并理解选项

- 区分服务连接、模型选择、功能使用哪个服务，以及外观偏好。
- 减少重复标题与卡片嵌套，提高分组、摘要和搜索定位的作用。
- 深色与大字号下，表单、长地址、错误提示和底部操作都完整可达。
- “已填写配置”和“连接验证成功”分别表达，错误说明尽量指向可执行的修复操作。
- 对独立服务分配、导入导出、技能与预设管理做统一体验检查。

### 6.6 星岛与 Clawd：形成 Aster 的辨识度

- 把星岛作为有代表性的精修对象，检查常驻、按压、展开、内容出现、收起和中途反向的全过程。
- 保留摄像头入口、墨线轮廓和展开内容之间的空间联系，改善层次、触感和过渡。
- App 页面与独立悬浮窗口的主题、文字和按钮风格一致；深浅色切换、系统栏、横竖屏及焦点行为可靠。
- 屏幕框选、快捷问答和剪贴板相关动作保持可理解的反馈，框选与确认的位置准确。
- Clawd 与输入区域协调，点击和位置反馈一致；其活动强度适合阅读与创作。

星岛有独立的 View、窗口和物理实现，不能只调整 Compose 页面就视为全局升级完成。

## 7. 性能与加载：先解决原因，再照顾等待体验

请用实际证据定位主线程工作、重组、测量、绘制、图片解码和 WebView 初始化等开销，再选择实现方式。可参考 [Compose 性能最佳实践](https://developer.android.com/develop/ui/compose/performance/bestpractices)，控制高频状态读取范围，并避免在重复执行的界面路径里进行昂贵计算。

在性能确实受限的环节，可以使用稳定占位、保留上一份内容、分阶段展示、短距离位移和柔和渐显，让等待过程保持连贯。用户操作和任务状态应当及时、真实地反馈。

具体检查重点：

- 流式文本尽量只更新当前需要变化的内容，避免整页或历史消息反复参与昂贵处理。
- 大列表有稳定标识与合理复用，移入视口的复杂卡片分批准备。
- 动画尽量使用合适的绘制或图层阶段，控制不必要的布局测量和大面积离屏效果。
- 缓存有正确的更新与释放条件，图片、WebView、播放器和动画不会长期无效占用资源。
- 正文、草稿、任务结果与错误信息的显示不被装饰动画延后。

对比请使用同一设备、相近系统状态和相同内容，优先选择可代表发布体验的构建。记录典型操作的帧耗时、长帧或掉帧情况以及关键等待，而不仅是平均 FPS。若没有测量条件，就明确记录主观观察，不填写推测的提升百分比。

## 8. 实施优先级与协作方式

### 第一优先级：做出完整的核心体验

先审查当前 App，整理影响最大的几项问题，建立基础令牌和公共组件，完成“侧栏 → 会话 → 模型选择 → 输入胶囊 → 流式回复 → 阅读”的原生标杆链路，并覆盖 RP 的关键阅读与 HTML 预览。

这个阶段应产生可安装、可体验的实际结果，以及关键界面的前后对比。样板完成后即可展示，其余独立工作可以继续推进。

### 第二优先级：把品质覆盖到全 App

将标杆中的规则扩展到创作、下载、设置、星岛和次级面板，补齐深色、错误、加载、空状态与大字号。通过公共组件改进整片界面，避免逐页形成新的例外。

### 第三优先级：完成精修与交接

集中处理真机上仍能感知的卡顿、突兀过渡、布局瑕疵和交互问题，整理参数、改动记录、必要验证和安装包。

如果可投入时间有限，优先交付第一优先级的完整成果，再扩展覆盖面。未完成项按价值排序留下，不把大量半成品页面混入交付。

普通样式、组件和动画参数请自主判断。涉及功能删减、产品流程大变、请求策略或数据迁移的调整，应先单独说明影响和替代方案，方便我判断。

## 9. 必须保住的产品边界

- 现有聊天、RP、绘图、下载、星岛、文件、预设和配置能力应继续可用，优化前后的关键结果可以对照。
- 模型与服务的分配、生成参数、提示词处理、工具执行及计费相关行为沿用现有产品约定；发现故障时单独定位处理。
- 剧情插图的文字提炼与绘图服务各有配置约定，界面整理不能混淆其来源或静默切换渠道。
- 包名、原发布签名、既有数据和升级覆盖安装能力应保留；若确需迁移，应提供迁移与回退说明。
- 保留角色卡前端的使用边界、脚本授权和既有沙盒约束。
- 保留阅读偏好、草稿、输入选区及合理的页面恢复行为，避免通过重建整个页面实现简单动画。
- 源码和交付材料中不包含真实服务密钥或签名私钥。

## 10. 怎样验收，以及需要做多少测试

采用“必要验证 + 真机体验 + 前后对比”的方式。优先复用现有检查，只为有实际风险的状态、生命周期和行为补充针对性验证；样式与参数微调不要求逐项新增单元测试，也不要求每次调整都跑全量 CI。

| 验收场景 | 通过标准 |
| --- | --- |
| 聊天核心链路 | 模型选择、输入、发送、停止和继续阅读顺畅；常用操作层级清楚 |
| 输入法与草稿 | 中文组合输入、光标和选区正常；连续开关键盘不丢草稿、不遮住发送操作 |
| 长文与流式输出 | 阅读位置稳定；回看历史不会被强行拉回；长消息和混合内容滚动连贯 |
| RP 与卡片 | 配置和消息操作可用，HTML 首帧衔接自然，原卡片样式与交互保持有效 |
| 页面与弹层 | 快速切换、连续开关、拖动取消及反向操作时，画面和最终状态正确 |
| 创作与下载 | 参数、任务进程、预览、保存、失败恢复都能找到且正确反馈 |
| 设置与导航 | 搜索、服务配置、长文本和返回行为清楚可用 |
| 星岛 | 常驻、展开、收起、框选及问答的关键路径可靠，主题与主 App 协调 |
| 适配 | 核心界面覆盖深浅色、小屏与大字号；关闭系统动画后功能完整 |
| 更新安装 | 最终包可使用原签名覆盖安装，原有会话与配置正常保留 |

这些场景按受影响范围合并检查，避免在每个页面重复同一套组合。日常联调优先使用本地样例、已有结果和 Mock，真实付费模型只在确需核实接口行为时使用。

最终希望看到：

1. 核心页面有可辨认的品质提升，层级、排版和控件一致。
2. 触摸、键盘、滚动与状态切换形成连续体验，动画能跟随用户节奏。
3. 重内容加载有妥善衔接，性能问题有定位和处理依据。
4. 原有关键功能、配置与数据可继续使用。
5. 对仍未解决的问题，有诚实、明确的说明。

视觉效果通过同内容、同设备的前后截图核对；动画与手感用短录屏和真机操作核对。模拟器截图与构建成功不能替代真机流畅度验收。
